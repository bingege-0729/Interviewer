# Interviewer · AI 模拟面试平台

面向求职者的 AI 模拟面试平台后端。按业务域拆分为账户、商品、智能面试三个服务，网关统一入口，耗时任务经消息队列异步处理。

> 当前进展：账户服务与网关路由已打通并验证；异步链路与缓存处理已实现，联调中。详见 [当前进度](#当前进度)。

## 架构

```
                         ┌──────────────────────────┐
   Vue3 Web ────────────▶│        Gateway :8000     │
                         │  路径路由 · 全局 CORS     │
                         │  内部接口黑名单拦截       │
                         └───────────┬──────────────┘
                    ┌────────────────┼────────────────┐
                    ▼                ▼                ▼
            ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
            │account :8081 │ │product :8083 │ │  ai  :8082   │
            │  account_db  │ │ product_db   │ │    ai_db     │
            └──────┬───────┘ └──────┬───────┘ └──────┬───────┘
                   └──────── Nacos 服务注册 ─────────┘
                              │
                   RabbitMQ ──┴── 权益发放 / 延迟校验
                                  面试生成 / 简历解析
```

**请求路径**：客户端只访问 `:8000`，网关按 `Path` 前缀转发到对应服务（`lb://` 经注册中心负载均衡），服务之间通过 OpenFeign 调用，不直连。

## 设计要点

### 1. 服务拆分与库表隔离

按业务域拆分为三个服务，各自独立库表（`account_db` / `product_db` / `ai_db`），不做跨库 JOIN。

**拆分依据**：三个域的数据变更频率和访问模式差异大——账户是高频读、商品是低频写、AI 面试是长耗时任务。拆开之后 AI 服务的线程池被长任务占满时，不会影响登录和下单。

**代价**：跨服务不再有本地事务。下单与权益发放之间是最终一致，靠 MQ 通知 + 重试 + 延迟校验兜底，而不是强一致。

### 2. 跨服务鉴权

登录态在网关侧完成校验，服务之间通过 Feign 的 `RequestInterceptor`（`FeignRequestInterceptor`）把 token 透传到下游，下游用统一的登录拦截器解析。

这样做的好处是：**每个服务不用各自实现一套鉴权逻辑**，新增服务只要引入 `common` 并注册拦截器即可。

### 3. MQ 异步与消费可靠性

耗时任务（面试内容生成、简历解析）走 RabbitMQ，接口立刻返回，避免占用请求线程。

消费端统一采用**手动确认**：

```java
channel.basicAck(tag, false);        // 业务处理成功 → 确认
channel.basicNack(tag, false, false); // 业务处理失败 → 拒绝，且不重回队列
```

**失败为什么不让消息回队列**：如果失败是代码缺陷导致的，回队列会立刻重新投递、再次失败，形成无限重投，打爆 CPU 和日志。所以直接丢弃，靠日志发现、人工介入。

**代价**：消息会丢。正规做法是配置死信队列留档，这一项在[待办](#待办)里。

### 4. 缓存与并发控制

第三方凭证（如微信 `access_token`）缓存在 Redis。凭证过期瞬间会有大量请求同时回源，用「分布式锁 + 双重检查」收口：

1. 缓存未命中 → 抢锁
2. 抢到的请求去刷新凭证并回填
3. **拿到锁后重新查一次缓存**（双重检查）——排队期间可能别人已经刷新好了，避免重复回源
4. 没抢到的短暂等待后重试

锁带超时，避免持锁进程异常时永久阻塞。

## 本地运行

### 1. 启动中间件

```bash
docker compose up -d
```

拉起 Nacos（`8849`，容器内 8848）、Redis（`6379`）、RabbitMQ（`5672` / 控制台 `15672`）。
MySQL 使用本机实例（`3306`），需自行建库。

### 2. 初始化数据库

执行 `dcloud-interview-web/sql/` 下的建表脚本，创建三个库并导入：

- `account_db` —— 账号、权益、权益任务、使用流水
- `product_db` —— 套餐、权益项、订单、Banner
- `ai_db` —— 简历、面试、轮次、问答、报告

### 3. 配置环境变量

项目通过 `dotenv` 读取根目录 `.env`（已在 `.gitignore` 中排除）。

```bash
cp .env.example .env
# 按实际环境填写
```

必需项：`MYSQL_*`、`REDIS_*`、`RABBITMQ_*`、`NACOS_*`、`DASHSCOPE_API_KEY`（AI 模块）。
可选项：`OSS_*`（头像/题图存储）、`SMS_APP_CODE`（验证码），不配置不影响账户与网关链路启动。

### 4. 启动服务

启动顺序：`gateway` 与业务服务无强依赖，但需 Nacos 先就绪。

```bash
# 各模块分别启动，或在 IDE 中运行对应 Application
java -jar gateway/target/gateway.jar
```

| 服务 | 端口 |
|---|---|
| gateway | 8000 |
| account-service | 8081 |
| ai-service | 8082 |
| product-service | 8083 |

### 5. 验证

```bash
# 经网关访问账户服务
curl http://127.0.0.1:8000/api/v1/account/...

# 直接访问内部接口应被网关拦截
curl http://127.0.0.1:8000/api/v1/account/benefit/task/updateStatus
```

## 待办

按优先级排列，都是当前设计上已知的缺口：

- [ ] **服务间容错**：Feign 超时与重试配置、Resilience4j 熔断降级（当前一个服务变慢会拖住上游）
- [ ] **死信队列**：消费失败的消息目前只打日志，应转入死信队列留档，支持事后补偿
- [ ] **凭证外部化**：大模型与支付参数仍写在配置文件里，应统一迁移到环境变量
- [ ] **单元测试**：核心链路（支付回调、权益扣减、幂等）缺测试覆盖
